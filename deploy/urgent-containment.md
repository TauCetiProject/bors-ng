# Prefer diagnostic remainders and recover private lint origins

The 3 November staging audit found 27→14+13→7+7 isolation of the same private
`slopeSetoid` lint, repeated singleton confirmation of located suspects, and
large retained groups waiting behind legacy singletons.

## Scheduling and provisional repair

Within an unchanged explicit priority, prefer sealed, multi-member diagnostic
remainders, largest first, then original admission age. Running work and higher
maintainer priorities still win. These groups are likely useful work, not proven
green: dispatch and promotion retain every existing head/base/approval/CI guard.
Normal eligibility deadlines remain independent of ordering.

The native partition records the non-suspect groups as `diagnostic_remainder`.
All suspect components, including multiple singleton units, retain their original
reason. Existing `provisional_remainder` admissions receive the preference too.
Legacy groups can recover the same scheduling role through one bounded journal
join, only when an exact two-part immutable partition proves every retained
head's membership outside the suspect group. More complex legacy splits remain
ambiguous. The annotation is read-time only; historical admissions are not
rewritten. A per-head
`remainder_retries` counter saturates at four; only the first three removals can
earn preference. Neutral invalidation cannot reset it. The existing failed-retry
age fairness limit still applies to ordinary/inconclusive retries; a newly
located removal earns its independent, bounded remainder allowance even if old
conflicts/bisections exhausted generic inherited age. No patch priorities are
rewritten.

A root failure's reserved successor no longer blocks the existing atomic
provisional handoff. Native terminal completion invalidates all descendants and
requeues their own members with approvals. A crash after atomic parent retirement
is still fenced by the train's predecessor guard. A child can use provisional
repair only after its exact predecessor has actually promoted and its tested
base is that landed commit, still matching live main. Pending, failed or
superseded predecessors cannot authorize individual blame. Other exclusions
remain: bundles, manual approvals, keep/hold
labels, automatic bumps, changed heads/main, withdrawals and ambiguous owners.
Provider hints still group retries rather than authorize repair; their retained
non-suspect group can now go first.

## Private module origins

For an otherwise unlocated environment-linter finding, a strict Lean private
prefix `_private.TauCeti.Module.<counter>.<declaration>` identifies a candidate
module path. Quoted/ambiguous modules, foreign namespaces, missing counters,
unowned paths and multiple changed owners stay unknown.

The optional offline helper verifies that each proposed path is a regular blob
at the exact candidate commit. It neither fetches nor evaluates source. The
existing five-second, eight-path, 256 KiB-per-blob and 512 KiB total bounds apply.
Generation, commit, base, member heads/digest, trusted workflow, run attempt and
job IDs must agree with immutable assembly provenance. Failures leave the raw
unknown diagnostic intact. Mixed unknown findings cannot become fully located.

Resolved findings record `origin=verified_private_module`, retaining the original
unknown reason. No source positions are invented. The journal retains raw output
and source identities; ownership is scheduling-only evidence, not a claim that a
PR introduced an old declaration's lint failure. Exact owners use the existing
`needs-rebase` provisional repair mechanism and its existing bounded fallback.
Older complete private-origin observations can be reconsidered after deployment,
subject to normal current-generation guards; historical recovery cannot withdraw
or reapprove a PR on its own.

## Validation and live rollout

Regression fixtures replay candidates 1864 and 1914 using source identities
retrieved from their exact tested commits. Both map the repeated lint to #26212;
invalid sources, stale identities and ambiguous ownership remain unknown. Tests
exercise the complete private-origin→provisional-repair path, a parent with an
actual reserved child, restart idempotency, priority/size ordering, preference
exhaustion and multiple singleton suspect components. Real Git tests verify the
offline single-source operation, missing paths and request bounds.

Use hosted CI and normal upstream merge/automatic deployment. Keep admissions
and running staging builds enabled. Verify the deployed image, health, continued
controller completions and natural queue selection. Record runtime observations
separately from the exact historical reproduction; no future catch-up rate is
claimed by the tests.
